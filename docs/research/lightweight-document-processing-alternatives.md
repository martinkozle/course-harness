# Lightweight document processing alternatives

Researched 2026-10-11 from vendor documentation, source repositories, PyPI release metadata, and a small local measurement in scratch virtual environments (CPython 3.14.6, 4 CPU threads, Linux). This note extends [Unstructured document parsing options](unstructured-document-parsing-options.md) (2026-09-20). It does not repeat that note's coverage of Docling, LiteParse, LlamaParse, Tavily, Mistral OCR, Google Document AI, Azure Document Intelligence and Amazon Textract, except where a fact changes the recommendation. Prices, free allowances and model names change often. Treat every number as dated 2026-10-11.

**Source access caveat.** The research environment's egress proxy blocked direct fetches from most vendor documentation sites (`ai.google.dev`, `docs.mistral.ai`, `developers.llamaindex.ai`, `datalab.to`, `unstructured.io`, `reducto.ai`, `landing.ai`, `mathpix.com`, `jina.ai`, `openrouter.ai`, `developers.openai.com`). For those vendors, claims were checked against the official page through a search index restricted to the vendor's own domain. They are marked **(index)**. Re-read those pages before relying on them. These sources were read in full: PyPI JSON metadata, GitHub source and READMEs (`raw.githubusercontent.com`, including Cloudflare's docs repository), installed package source, and Anthropic's docs (`platform.claude.com`).

## Recommendation

**1. Make `docling-slim` without models the zero-configuration default, and use its model-free `NativePdfPipeline` for PDFs.** `docling-slim[format-pdf,format-office,format-html]` installs without PyTorch, model weights or a download-consent step. It keeps the `DoclingDocument` JSON and per-page export path that [`docling_parser.convert_document`](../../src/course_harness/docling_parser.py) already uses. The local measurements in this note are on a synthetic corpus, not a quality benchmark:

| Measured locally (2026-10-11) | Docling Slim, no models | Full Docling (prior note) |
| --- | --- | --- |
| Virtual environment, empty venv plus the package | **209 MB** | about 1.7 GB venv plus about 730 MB models |
| 102-page born-digital PDF | **1.6 s**, 369 MB peak RSS | not re-measured; the prior note calls CPU PDF conversion slow |
| 3-slide PPTX / small DOCX / HTML | 0.4 s / 0.3 s / immediate, with slide numbers in `document.pages` | same code path (DOCX/PPTX never needed model weights) |
| PDF provenance | page number plus bounding box per text line | page number plus bounding box per layout item |

The trade-off is fidelity. The package docstring for `NativePdfPipelineOptions` says it "runs no layout, OCR or table-structure model", so output has "one plain `TextItem` per text cell in the parser's order, without reading order, headings or tables" (`docling/datamodel/pipeline_options.py` in [docling-slim 2.137.0](https://pypi.org/project/docling-slim/2.137.0/)). In the two-column test page it merged the left and right columns line by line. It also returns nothing for scanned pages. That is acceptable for a default only if Course Harness can detect a poor result and offer something better (point 3). The maintainers' own packaging reference lists "PDF → Markdown/JSON, no ML" as a supported `docling-slim[format-pdf]` recipe ([slim packaging reference](https://github.com/docling-project/docling/blob/main/docling/.agents/skills/docling/references/slim-packaging.md)). The default `DocumentConverter()` PDF path still imports `torch`. It failed with `ModuleNotFoundError: torch` until `NativePdfFormatOption` was selected explicitly. Slim 2.137.0 also needed `packaging` added by hand before its PDF backend would import. Pin and test that in `pyproject.toml`.

**2. Offer hosted processing behind a key, preferring credentials the Course Author already has.** ADR 0014 already detects `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY` and Bedrock credentials. Reusing one of these is the lowest-friction hosted route, and it needs no new vendor account:

- **OpenRouter key: PDF via the `file-parser` plugin.** The `cloudflare-ai` engine is documented as free and the `mistral-ocr` engine is billed per 1,000 pages ([OpenRouter PDF inputs](https://openrouter.ai/docs/guides/overview/multimodal/pdfs) **(index)**). The free engine is text-layer extraction, so it is no better than local extraction for scans (inference from Cloudflare's PDF method below). The value is `mistral-ocr` billed to an existing account.
- **Anthropic, OpenAI or Bedrock key: direct PDF input to a vision model, used as a "transcribe this page range to Markdown" OCR fallback for scanned or image-heavy pages only.** The estimated cost on Claude Haiku 5.5 is roughly **$0.7–0.9 per 1,000 pages**. This is an inference from documented token prices, not a measurement (see the hosted table). An LLM transcription can paraphrase or omit content, so it should be labelled and never be the silent default.

For a dedicated parser account, the best **recurring, no-card** free allowances found are **LlamaParse** (10,000 credits per month, which is 1,000–3,333 pages depending on tier) and **Datalab** ($10/month on a personal email, $20/month on a work email, both **(index)**). Mistral OCR has the lowest paid price ($4 per 1,000 pages, or $2 in batch), but its Free-plan credit amount could not be re-verified (see limits). Do **not** promote the Gemini free tier as a default. Google may use free-tier content to improve its products, and Google's terms allow only Paid Services when an app is made available to users in the EEA, Switzerland or the UK (see the hosted table).

**3. Move full Docling into an optional extra, `course-harness[docling]`, and route by capability, not by vendor.** Proposed shape (architectural opinion):

- **Dependencies.** Base: `docling-slim[format-pdf,format-office,format-html]` plus `packaging`. Drop `docling`, `torch` and `torchvision`, and the `pytorch-cpu` `[tool.uv.sources]` entries, from the base dependencies. Add an extra `docling = ["docling-slim[models-local,feat-ocr-rapidocr]"]` or `["docling>=2.137"]`, and keep the CPU-wheel index pinning under that extra. `python-pptx` is already a base dependency and keeps the speaker-notes code working.
- **One processor interface.** Each processor declares `name`, `version`, supported media types, whether it is installed or available, whether it sends content off the device, and `convert(media_type, bytes) -> (markdown, structured_json | None)`. Every processor must emit the same `# Page N` / `# Slide N` sectioned Markdown that `convert_document` emits today. Full-text search line coordinates and page or slide citations then stay processor-independent. Hosted parsers mostly return per-page Markdown, so this is a thin adapter.
- **Routing in `MEDIA_TYPE_PROCESSORS` / `process_snapshot`.** Office and HTML always go to slim, because full Docling adds nothing for them. For PDF:
  - Use full Docling if the extra is installed and models are ready.
  - Otherwise use the native pipeline.
  - If the native pipeline returns empty or very sparse text, for example fewer than about 100 characters per page on most pages (a threshold to tune), mark the Resource "needs OCR" instead of "failed". Then offer, per upload: install `course-harness[docling]` (the existing model-download consent flow in `app.py` moves behind the extra), or send the file to a configured hosted processor with explicit consent.
- **Cache identity.** `process_snapshot` writes to `derived/<content_hash>/`, keyed only by content hash ([`resources.py`](../../src/course_harness/resources.py)). If the processor changes, a stale `extracted.md` would be served. Record the processor name and version in the derived directory, either `derived/<hash>/<processor>@<version>/` or a manifest, so that installing the extra or adding a key can reprocess. This fits ADR 0007: derived data stays disposable.
- **Credentials and privacy.** Store a hosted parser key in installation credential storage, like Connector Credentials. Never store it in a Course Workspace (ADR 0007 and ADR 0014; `CONTEXT.md`). Offer detected keys but do not use them until added. Make "sends this document to <vendor>" an explicit per-upload or per-installation choice that is visible on the Resource.

**Why not MarkItDown or PyMuPDF4LLM as the default.** MarkItDown (MIT) handles DOCX, PPTX and HTML well, including slide numbers and notes. Its PDF converter, however, returns a single string with **no page boundaries**: zero form feeds in the measured output, built on `pdfminer.high_level.extract_text` or `pdfplumber`. Page-level citation would need a separate page splitter. Its base dependency `magika` also pulls in `onnxruntime`, so it is not smaller than slim (227 MB measured). PyMuPDF4LLM gave the best CPU-only PDF result in the test: it got the columns right, detected the table, and returns page chunks with boxes. It is **AGPL-3.0 or commercial**, as is its required `pymupdf-layout`. For an MIT-licensed package distributed on PyPI and serving an HTTP UI, that is a licensing decision for the maintainers, not a default dependency. This is opinion, not legal advice.

**Docling's Office path is already lightweight.** With `docling-slim[format-office]` and no models, the existing DOCX and PPTX conversion code ran unchanged and produced `document.pages` 1..N for slides. This confirms the prior note's statement that DOCX/PPTX need no model weights. It also means the heavy cost in today's install is entirely the PDF path.

**Independent quality signal, with a conflict of interest.** Datalab's Marker README reports olmocr-bench overall scores (1,403 PDFs). Docling on GPU scored 50.3, "Marker fast, no OCR" on CPU 43.6, and LiteParse on CPU 22.4 ([README](https://github.com/datalab-to/marker/blob/master/README.md)). Datalab sells the hosted Marker API, and the benchmark does not include Docling's native pipeline, MarkItDown or PyMuPDF4LLM. Use it only as a hint that text-layer-only tools lose substantially on scans, tables and reading order.

**Ranking for this project (opinion).**
1. Reuse an existing LLM or OpenRouter credential as a vision-OCR fallback for scanned pages.
2. LlamaParse or Datalab as the "dedicated parser" choice: both offer recurring no-card allowances, cover PDF, DOCX and PPTX, and return per-page structure.
3. Mistral OCR for cheapest paid volume.

Gemini paid tier is a reasonable comparator. Gemini free tier, Cloudflare, Jina, Mathpix, Reducto, LandingAI and Chunkr are weak fits: training or terms constraints, no PPTX, no gain over local text-layer extraction, one-time trials, or AGPL.

## Limits and unresolved checks

- **Mistral Free-plan credit.** The prior note's "$10/month in API credits" and whether OCR draws on it could not be confirmed today. Current docs describe "included monthly usage" without a figure **(index)**. Check in a real Free-mode account.
- **Gemini free-tier quotas** are no longer published as a table. The docs point to AI Studio's per-project view **(index)**. The EEA/CH/UK Paid-Services-only clause needs a maintainer reading for a self-hosted desktop app where each Course Author brings their own key. This note does not interpret it as legal advice.
- **Datalab** fast/balanced per-page rates and training policy were not found. The two free-credit descriptions (a $5 card-verified credit versus a $10–20 monthly no-card allowance) conflict across pages **(index)**.
- **Unstructured** free allowance conflicts between 10,000 pages one-time and 15,000 pages per month **(index)**.
- **OpenRouter `mistral-ocr` per-page price** and **OpenAI file-input size and page limits** were not verified.
- **Docling native pipeline quality** was measured only on a synthetic two-column PDF with a ruled table. Columns were interleaved line by line, and the table cells came out as text lines. Real lecture PDFs, especially slide exports, which are mostly single-column, may fare better. Untested.
- **Install sizes** are uv venvs in a scratch directory, not this repo's Nix-pinned environment. Shared packages already in the base install (Pillow, lxml, pydantic, numpy via other dependencies) reduce the incremental cost. The figures are "empty venv plus package", not deltas.
- **`docling-slim[format-pdf]` packaging gap.** 2.137.0 needed `packaging` installed manually before `NativePdfPipeline` imported. Pin and test in CI.
- **Scanned PDFs:** none of the zero-config options OCR. `docling-slim[format-pdf,feat-ocr-rapidocr]` (RapidOCR without torch) is documented by Docling ([slim packaging reference](https://github.com/docling-project/docling/blob/main/docling/.agents/skills/docling/references/slim-packaging.md)), but whether it runs with `NativePdfPipeline` or requires the layout model was not tested. It is a candidate middle tier between "native" and "full Docling".

## Suggested evaluation

1. **Prototype the default.** Switch base dependencies to `docling-slim[format-pdf,format-office,format-html]`, route PDF through `NativePdfFormatOption` when the `docling` extra is absent, and confirm the existing PDF/PPTX indexing tests pass with torch uninstalled. Measure installed size of the Nix-shell venv before and after.
2. **Corpus.** Reuse the prior note's set: two-column paper, scanned PDF, mixed text/image PDF, table-heavy PDF, PPTX with screenshots and notes, DOCX with tables, multilingual scan. Add a slide-deck PDF export, since that is the commonest course PDF.
3. **Candidates.** Docling native; Docling full (extra); `docling-slim` plus RapidOCR; MarkItDown (baseline); PyMuPDF4LLM (quality reference only, given AGPL); LlamaParse Cost-effective; Datalab balanced/accurate; Mistral OCR; Claude Haiku 5.5 page transcription via an existing key.
4. **Scores.** Missing text, reading order, table integrity, page/slide attribution correctness, time, peak RSS, cost per 1,000 pages, failure behaviour. Add the **sparse-text detector's** precision: does it flag the scans and image-only slides, and nothing else?
5. **Decide.** Choose the default "needs OCR" offer: a local extra or a hosted key. Decide whether a hosted processor should ever run without per-upload confirmation.
