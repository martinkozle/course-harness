# Carry Release files in a Git ref per Release

A Course Release's template and Artifact bytes (`inputs/template.pptx`, `artifacts/<id>.pptx`) live in Course Harness's local Release data, outside the Course Workspace, so a Git remote could not serve them to the Classroom. After a Release is named, Course Harness also writes, with Git plumbing only and as best effort, a parentless commit whose tree holds exactly those files, and points `refs/course-harness/release-files/<slug>` at it; publishing never fails or rolls back because of it. The commit is derived only from the manifest and the bytes, so writing it again yields the same commit and a pushed ref never needs a forced update. Push first backfills the ref of any Release that lacks a correct one from local Release data, then sends the `main` branch, the `course-release/*` tags and these refs; a ref that is wrong and cannot be corrected locally is reported and left out rather than blocking the rest. A reader fetches `+refs/heads/main`, `+refs/tags/course-release/*` and `+refs/course-harness/release-files/*`. The working tree and the Course branch never contain the binaries, and ADR 0009 still holds: the manifest is authoritative, so a reader refuses a missing or extra file, checks each Artifact's exact size before reading it and its SHA-256 after, and checks the template's SHA-256 after reading it; the manifest records no template size, so the template's size is checked only against the size cap. We chose a ref per Release over committing binaries to the branch (which would bloat every clone of the Course history and blur canonical state with generated files), Git LFS (an extra server-side service and client dependency), and release assets on a forge (not portable across hosts and not readable from a plain mirror). The cost is refs that a plain `git clone` does not fetch, so a reader names them explicitly.
