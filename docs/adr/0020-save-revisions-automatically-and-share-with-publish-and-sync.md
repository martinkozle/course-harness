# Save Revisions automatically and share with Publish and Sync

Course Revisions are a safety net, like an editor's local history, so a Course Author never has to manage them to share work. Before Publish or Sync, uncommitted edits become a Course Revision on their own, with a deterministic summary built from what changed ("Edited Lecture 2 'Building an MCP Server', the Quiz for Lecture 3 and the Course Plan"); this needs valid, provenance-clean Current State, and otherwise nothing is saved and the findings are shown with a way to ask the Course Agent to fix them. Files changed outside Course Harness are never saved automatically: they still go through History, as ADR 0006 requires. This refines ADR 0006: Revisions at milestones the Course Author names remain possible from History, but no other flow requires visiting it.

The header shows **Publish** with the number of Revisions that no Release covers (uncommitted edits count as one more), and **Sync** with what it would send and receive. Sending counts local `main` commits the remote lacks, one per Release whose tag or files ref the remote lacks, and uncommitted edits; receiving counts remote `main` commits this computer lacks. A Release whose files ref the last push left out as not matching its manifest is reported once and no longer counted. The counts are read locally against the last check of the remote: `git ls-remote`, then one fetch (`--no-tags --refmap=`) of `main` into `refs/remotes/origin/main` and of any Release tag this computer lacks, never forced, so local tags are never replaced; a fetched tag that is not a valid Release here is deleted again. Release files refs are only compared, never downloaded. The commit actually fetched (`rev-parse` after the fetch) is what Sync moves to. Releases pushed from elsewhere count as Releases, their Revisions are not changes, and their IDs cannot be reused. The check runs in the background when a Course opens, on window focus and every five minutes, without any sign-in prompt (no askpass, no interactive credential helper); its result is kept in `.git/course-harness-remote-check.json`, beside the repository's other private records, and failures only show in the Sync tooltip and its accessible name. One lock per Workspace serialises every check, push and Sync, so two fetches never write the same ref at once.

Sync first receives the remote's Revisions when this computer's `main` is an ancestor of the remote's and the uncommitted edits touch none of the incoming files, then saves the edits as an automatic Revision on top and pushes as ADR 0019 describes. It never merges or rebases. When both sides have Revisions the other lacks, nothing is sent or received and the Course Author chooses, after a confirmation that explains it: **Use the remote's version** saves the edits as a Revision, keeps this computer's `main` under `refs/course-harness/kept/<time>-<commit>`, and moves `main` and the files to the remote's; **Replace the remote's version with this computer's** pushes `main` with `--force-with-lease` against the commit the check fetched, so a newer push elsewhere is never overwritten, and never forces or deletes Release tags or files refs. While the remote has Revisions this computer lacks, the header and Publish say "The remote has newer changes; sync first".

Publish runs the automatic Revision, names the Release with optional notes ("What changed", stored in the manifest only when present so older manifests stay exact, and shown beside the Classroom's Release selector), and, when "Push to <remote>" is ticked, pushes. A failed push keeps the Release, and Sync still shows it as waiting to be sent.

Moving `main` (receiving, or using the remote's version) runs as a History transaction. When no uncommitted edits are kept, provenance is prepared before `main` moves and finished after, like a new Revision, so a crash leaves either the old state or one that recovery completes. When edits are kept, a crash after `main` moves and before provenance is written leaves the kept files as Workspace Drift for review; this window is the length of one small file write.

Manifests stay strict. A reader refuses a manifest with fields it does not know rather than ignoring them, because the manifest is verified as exact canonical JSON of what the reader understands and an unknown field might change what the Release means; the refusal says the Release came from a newer Course Harness. So a Classroom must be upgraded before Releases are published with a newer Course Harness (this one adds `notes`).

The remote stays the ordinary `origin` and lives in Settings > Git remote. Besides pasting a Git URL, a Course Author with the GitHub CLI signed in can create an empty repository through their own `gh` (`gh repo create github.com/<owner>/<name> --description=<title>`, then the SSH or HTTPS URL matching `gh config get git_protocol`); Course Harness holds no GitHub token. For development, `COURSE_HARNESS_ALLOW_LOCAL_REMOTES=1` also accepts an absolute local path.

We chose a fast-forward-only Sync with two explicit ways out over automatic merges because Course state must stay valid and reviewable, and a merge of canonical YAML could produce state no one reviewed; diverged history is rare for a single author and is better resolved deliberately.

The interface first called this "sharing" ("Share to GitHub", "the shared copy", Settings > Sharing). That copy now uses the Git terms it stands for: Publish's checkbox reads "Push to <remote>", the setup dialog is "Connect a GitHub repository" or "Connect a Git remote", Settings has a "Git remote" section with "Remove remote", and the diverged choices name the remote's version. Behaviour, endpoints and code identifiers such as `use-shared-copy` and `useSharing` are unchanged.
