# Save Revisions automatically and share with Publish and Sync

Course Revisions are a safety net, like an editor's local history, so a Course Author never has to manage them to share work. Before Publish or Sync, uncommitted edits become a Course Revision on their own, with a deterministic summary built from what changed ("Edited Lecture 2 'Building an MCP Server', the Quiz for Lecture 3 and the Course Plan"); this needs valid, provenance-clean Current State, and otherwise nothing is saved and the findings are shown with a way to ask the Course Agent to fix them. This refines ADR 0006: Revisions at milestones the Course Author names remain possible from History, but no other flow requires visiting it.

The header shows **Publish** with the number of Revisions since the newest Release (uncommitted edits count as one more), and **Sync** with what it would send (local `main` commits, Release tags and Release files refs that the remote lacks, plus uncommitted edits) and receive (remote `main` commits). The counts are read locally against the last check of the remote: `git ls-remote` for the remote's refs, and a fetch of only `main` into `refs/remotes/origin/main`, so a check never downloads Release files. The check runs in the background when a Course opens, on window focus and every five minutes; its result is kept in `.git/course-harness-remote-check.json`, beside the repository's other private records, and its failures only show in the Sync tooltip.

Sync saves an automatic Revision, then receives the remote's Revisions only when that is a fast-forward of a clean Current State, and otherwise explains it in plain words and changes nothing; it never merges or rebases. It then pushes as ADR 0019 describes. Publish runs the automatic Revision, names the Release with optional notes ("What changed", stored in the manifest only when present so older manifests stay exact, and shown in the Classroom's Insights), and, when "Share" is ticked, pushes. A failed push keeps the Release, and Sync still shows it as waiting to be sent.

The remote stays the ordinary `origin` and lives in Settings. Besides pasting a Git URL, a Course Author with the GitHub CLI signed in can create an empty repository through their own `gh` (`gh repo create`, then the SSH or HTTPS URL matching `gh config get git_protocol`); Course Harness holds no GitHub token. For development, `COURSE_HARNESS_ALLOW_LOCAL_REMOTES=1` also accepts an absolute local path.

We chose a fast-forward-only Sync over automatic merges because Course state must stay valid and reviewable, and a merge of canonical YAML could produce state no one reviewed; diverged history is rare for a single author and is better resolved deliberately.
